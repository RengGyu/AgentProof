# AgentProof 문제 해결 사례집

수정 기준: 2026-09-21. 이 파일은 제품의 동작 명세가 아니라 과거 문제에서 기술을 배우는 사례집이다. 현재 제품의 전체 흐름은 수정된 02를 우선한다. 한 번에 한 사례씩 공부하되 기록은 전체 학습을 마쳤을 때 남겨도 된다. 출처 키는 04 문서에 있다.

## 읽기 전에: 제품과 평가의 구분

제품은 GitHub 연동으로 PR 자료를 수집하고 검토 근거를 전달한다. 아래 테스트·실험들은 그 제품의 일부 동작이나 판단을 확인한 자료다. 테스트 스크립트가 분석 서버를 호출했다고 제품의 정상 사용도 항상 그 스크립트나 수동 URL 입력을 거친다는 뜻은 아니다.

| 사례 | 실제 제품에서 연결되는 문제 | 근거 수준 |
|---|---|---|
| 1 | 근거를 해결 판정으로 과장하지 않기 | 과거 설계 제안 |
| 2 | 테스트 코드와 검토 대상의 관계 연결 | 과거 로컬 수정·검증 기록 |
| 3 | LLM 결과를 서버 데이터로 받아들이는 계약 | 과거 분류기 설계·진단, 현재 출력 schema 아님 |
| 4 | 정보 추가가 정확도·비용에 미치는 영향 | 과거 문장 분류 비교, 현재 코드 추천 점수 아님 |
| 5 | 충족 판정과 검토 후보 표시 분리 | 당시 오프라인 표시 실험 |
| 6·7 | 필요한 코드 범위를 공급하고 유용한 위치 고르기 | 저장된 실제 PR 응답에 대한 감독 감사 |
| 8 | 외부 자료 수집·출력 처리 실패를 의미 오류와 구분 | 평가 중 관찰한 사례, 전체 운영 인증 아님 |

현재 코드의 기본 처리 경로는 `github.ts` → 보고서/검토 안내 모듈 → `pr-evidence-review.ts` → 화면이다. 자동 분석은 webhook/worker, 수동 분석은 `/api/analyze`에서 시작하며 조건과 후속 처리가 다를 수 있다. 아래 과거 분류 기술을 모두 그 경로의 현재 필수 단계로 가르치지 않는다.

## 사례 1 — 테스트와 CI가 있으면 목표를 달성한 것인가?

**당시 문제:** 8/13 설계는 ‘repository overview를 더 유용하게’라는 목표에 함수·문자열 테스트·성공한 CI가 연결돼도 사용자 유용성을 입증하지 못한다고 지적했다. 모호한 단어 목록을 늘리는 방식의 한계도 명시했다. [E1: 당시 설계]

**도입 개념:** objective(목표), verification contract(성공 기준), observed evidence(관찰)를 분리한다. ‘테스트가 있다’와 ‘그 기준을 검증한다’는 별개다.

**왜 기술적인가:** 데이터 모델에서 서로 다른 사실을 같은 boolean으로 합치면, 나중에 화면에서 문구만 바꿔도 오류가 남는다. 상태 집계가 어떤 입력을 근거로 하는지부터 설계해야 한다.

**한계/현재 연결:** 강한 자동 판정에는 유용한 경계지만, 관련 코드 안내까지 승인된 성공 기준을 요구하면 제품 효용을 막을 수 있다. 현재 검토 안내는 충족 판정과 분리하는 방향이다.

**교육용 예:** `testExists=true`, `jobSuccess=true`, `requirementSatisfied=unknown`은 모순이 아니다.

**질문:** ‘검색이 빨라져야 한다’를 측정 가능한 기준으로 바꾸려면 어떤 환경·입력·측정값이 필요한가? 그것이 없어도 무엇을 보여줄 수 있는가?

## 사례 2 — 관련 없는 import 하나가 테스트 판정을 바꾸는 문제

**당시 문제:** 8/18 문서는 같은 모듈에서 여러 함수를 import하면 직접 assertion 수를 0으로 처리하는 경로를 기록했다. 단일 import만 있는 합성 테스트는 이 문제를 놓쳤다. [E2: 로컬 구현·검증됐다고 기록된 문서, 이번 재실행 아님]

**해결 원리:** ‘파일의 import가 하나인가’가 아니라 ‘검토 대상 함수에 연결된 binding을 하나로 식별할 수 있는가’를 본다. export 이름, 로컬 alias, 실제 assertion에서의 사용을 연결한다.

```ts
// 교육용 예시, 실제 프로젝트 코드 아님
import { save as persist, format } from './service';
expect(persist('x')).toEqual('x');
// format을 함께 가져왔다는 이유만으로 persist 관계가 무효가 되지는 않는다.
```

**한계:** 정적으로 연결됐어도 실행됐다는 뜻은 아니다. mock·동적 import·간접 호출을 모두 해결했다고 주장할 수 없다.

**과적합과의 차이:** 특정 함수명을 예외 처리하는 대신 ‘대상에 무관한 import 추가가 기존 관계를 깨지 않아야 한다’는 일반 성질을 테스트한다. 이것은 metamorphic testing(의미를 유지하는 변형으로 확인)의 학습 예시다.

**질문:** 로컬 이름이 alias로 바뀌어도 같은 대상을 찾으려면 어떤 정보가 필요한가?

## 사례 3 — LLM에게 같은 결정을 두 번 쓰게 하면?

**당시 문제:** 9/2 설계에는 span의 역할과 그 역할에 맞는 목표 그룹을 모델이 각각 작성하다 불일치한 사례가 기록돼 있다. 25개 진단 중 invalid 6건이 중복된 역할/그룹 계약을 위반했다고 보고했다. 이는 과거 실행이지 현재 Gemini 통계가 아니다. [E3]

**접근:** 모델은 span 역할을 한 번 결정하고, 그 결정에서 파생 가능한 그룹은 서버가 만든다는 설계였다.

**기술:** single source of truth, 정규화, 파생 데이터, schema, 런타임 검증. TypeScript 타입은 빌드 시 개발자를 돕고, 외부 JSON 검사는 실제 응답을 처리할 때 필요하다.

**주의:** JSON이 유효해도 역할이 틀릴 수 있다. 반대로 JSON이 깨졌다고 원문을 이해하지 못했다고 확정할 수 없다. 형식 성공률과 의미 정확도를 나눠야 한다.

**질문:** 어떤 필드는 모델이 판단해야 하고, 어떤 필드는 코드가 계산해야 하는가? ‘추천 이유’도 기계적으로 파생 가능한가?

## 사례 4 — 문맥을 더 줬는데 오분류와 비용도 늘었다

**기록:** 9/14 B/C 60개 비교에서 당시 machine-reviewed 요구사항 보존은 66/92→73/92, 비요구사항의 요구사항 승격은 10/385→13/385, 토큰은 98,320→239,056으로 기록돼 있다. human gold가 아니며 현재 코드 추천 정확도와도 다른 지표다. [E4]

**배울 점:** 더 많이 요구사항으로 분류하면 recall과 false positive가 함께 늘 수 있다. ‘문맥 추가가 더 똑똑하다’나 ‘규칙이 과적합됐다’ 중 어느 하나로 바로 결론내리지 않는다.

**기술:** precision/recall, 분모, 후보 선택 재현율, 라벨 신뢰도, ablation(한 요소만 바꾸는 비교), holdout(조정에 쓰지 않은 평가 자료).

**구조적 한계:** 뒤 단계가 후보 밖 항목을 복구할 수 없다면 최종 recall은 후보 단계 recall을 넘을 수 없다. 이 조건이 없는 모든 시스템에 무조건 적용하는 공식은 아니다.

**질문:** 10개 중 8개를 맞혔다는 말에서 누락된 정보는 무엇인가? 실패한 요청을 분모에서 빼면 어떤 문제가 생기는가?

## 사례 5 — 보고서는 생성됐는데 검토 카드는 0개

**기록:** 9/15 오프라인 기록에서는 26개 strict 요구사항이 있어도 목표 카드가 0개였다. 이후 assessment와 후보 표시를 분리한 실험은 26카드를 노출했지만, 명시적 첫 파일 추천 누락도 기록했다. 서로 다른 실험 단계이며 최신 10개 라이브 결과와 합치면 안 된다. [E4]

**원리:** ‘검증된 충족 여부를 보여줄 권한’과 ‘검토할 후보를 보여줄 가치’를 분리한다. 기존 계약을 망가뜨리지 않고 화면용 projection(별도의 표시 모델)을 둘 수 있다.

**주의:** 카드를 복구한 것은 표시 기능 개선이지 관련 코드 정확도 향상은 아니다. 조건을 다 풀어 아무 근거나 보여주는 것도 해결이 아니다. 실제 코드 참조와 출처 경계는 유지한다.

**질문:** 카드 표시율, 정확한 코드 도달률, 요구사항 해결률이 각각 무엇을 측정하는가?

## 사례 6 — AST와 코드 조각은 무엇을 해결하는가?

**문제:** 큰 파일의 앞부분만 읽거나 읽은 뒤 바이트 한도로 자르면 핵심 함수·조건이 빠질 수 있다. 파일 전체를 늘 보내면 비용과 지연이 늘고 관련 없는 내용도 많아진다.

**기술:** lexical 검색은 단어/식별자로 위치를 찾고, AST는 문법 경계를 파악하며, symbol/참조 분석은 이름과 선언의 연결을 다룬다. 이들은 같은 기술이 아니다. 현재 구현의 제한된 스캐너를 모든 언어의 정밀 AST 분석으로 부르면 안 된다. [E5]

**평가에서 관찰한 사례:** HTTPX #3783은 `_redirect_method`가 있는 492–511줄을 추천했으나 옵션을 확인하는 핵심 분기는 515–516줄에 있었다. 모델은 조각이 끊겼다고 명시했다. 첫 이동 위치는 유용하지만 그 공급 조각만으로 핵심 확인은 어렵다. 이것은 모델 입력·추천 범위의 문제이며, 실제 브라우저 화면에서 코드가 잘리는 현상을 관찰한 것은 아니다. 어느 단계에서 빠졌는지는 당시 저장 응답만으로 확정하지 못했다. [E6]

**핵심:** 저장소를 넓게 검색하는 것과 전체 코드를 LLM에 넣는 것은 별개다. 함수 전체를 무조건 보내는 방식도 거대한 함수에서 다시 한계에 부딪힌다.

**질문:** 입력에 핵심 분기가 없을 때 모델 교체 실험만으로 무엇을 알 수 있고, 무엇을 알 수 없는가?

## 사례 7 — 올바른 후보가 있는데도 잘못 고른 경우

**관찰:** Svelte #18839는 `:export` 특별 처리를 없애려는 목표는 이해했다. 하지만 첫 추천 `css-prune.js:23–33`을 ‘pseudo-class set에서 export가 제거된 곳’이라고 설명했다. 실제 23줄은 `whitelist_attribute_selector` 종료였다. 실제 변경은 `prune/ComplexSelector` 주변이며 head137–214가 보조 후보로 존재했다. [E6, 대화의 노폼 독립 재확인]

**기술적 분리:** 후보 발견과 최종 순위화·설명 생성은 다른 품질이다. 존재하는 파일과 해시가 맞아도 그 위치의 의미 설명은 거짓일 수 있다.

**미확정:** 삭제 전 base 코드나 변경 표시 부족이 원인일 가능성은 있지만 한 사례로 입증하지 못했다. 후보 순서 편향과 출력 변동도 별도 검사 대상이다.

**다음 실험 제안, 아직 미실행:** 같은 입력으로 반복 → 후보 순서만 변경 → 같은 예산에서 필요한 base/변경 정보만 추가. 여러 변수를 한 번에 바꾸면 개선 원인을 알기 어렵다. 현재 사례는 개발 진단군으로 두고 이후 미사용 자료로 확인한다.

**질문:** Svelte 파일명을 특별 취급하지 않고 같은 실패 유형을 재현할 작은 예시는 무엇인가?

## 사례 8 — 모델 문제처럼 보였던 인증·수집 문제

**관찰:** 9/20 첫 익명 실행은 Flask 추천, Starlette freshness 확인 실패, 나머지 8개 GitHub 조회 한도 초과였다. 사용자가 토큰 전달을 승인한 뒤 인증 실행은 10개 응답을 수집했고 Starlette도 목표와 추천을 반환했다. [E6]

이것은 당시 수동 API 평가의 인증 방식이다. 제품의 GitHub App 자동 분석은 installation access token을 발급해 자료를 수집하는 경로가 있다(`analysis-worker.ts`). 모든 사용자에게 매번 개인 토큰을 입력받는 것이 제품의 필수 사용 방식이라고 일반화하지 않는다.

**기술:** authentication(누구인가), authorization(무엇을 할 수 있는가), rate limit(기간별 요청 한도), timeout(한 요청 또는 전체 작업을 얼마나 기다리는가), deployment environment(실제 실행 설정).

**주의:** 토큰이 필요하면 비밀값을 채팅·보고서에 복사하지 않는다. 서버에 전달하는 자격증명의 목적·권한·보관을 구분한다. 계정 로그인 성공과 특정 Preview의 배포 권한은 동일하지 않다.

**관측 가능성:** 요청 시작/종료, 단계, 오류 종류, revision, 모델 설정을 기록하면 ‘호출 안 됨’과 ‘호출 후 잘못 판단’을 구분할 수 있다. 원문과 비밀값을 무조건 로그에 저장할 필요는 없다.

**추가 관찰:** Flask·Vite의 안전 문자열 치환은 일부 문장을 ‘the referenced code’로 바꿔 문법을 훼손했다. 보안/출력 처리 실패와 추천 위치 정확도를 분리해서 본다. 원인 경로는 확인됐지만 그 후 수정 완료를 이 자료는 주장하지 않는다.

**질문:** API 200 응답, JSON 통과, 코드 참조 일치, 유용한 추천은 왜 각각 다른 성공인가?
