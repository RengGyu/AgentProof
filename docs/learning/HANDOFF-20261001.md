# AgentProof 개발·학습·면접 핸드오프

기준일: 2026-10-01, 한국 시간. 이 문서는 새 ChatGPT 세션에 **하나의 파일로 첨부**하기 위한 통합 학습 자료다. 제품 목적, 현재 구조, 개발 중 판단과 실패, 운영 검증 범위까지 포함한다. 모든 과거 대화·브랜치의 전수 연대기는 아니며, 확인하지 못한 동기와 결과는 만들지 않는다.

GitHub: [RengGyu/AgentProof](https://github.com/RengGyu/AgentProof)

## 0. 새 AI가 먼저 알아야 할 기준

- 기준 소스: 작업 브랜치 `codex/recover-bounded-target-20260913`, 확인한 HEAD `3b3153433674b81d8a6e23730ad79ed72846728f` 및 그 위의 미커밋 변경.
- 최근 웹·모바일 공통 서버와 모바일 UI 변경은 미커밋 상태다. GitHub main, HEAD, 현재 로컬 소스, 배포된 소스는 자동으로 같지 않다. 이 문서도 작성 시점에는 로컬 파일이다.
- GitHub 코드가 없거나 다른 버전이면 사용자에게 해당 파일을 요청한다. 원격 파일을 읽지 않고 읽었다고 말하지 않는다. 오래된 README의 PAT·공유·로그인 설명을 최신 코드보다 우선하지 않는다.
- 신뢰 순서: 해당 버전의 실제 코드와 실행 결과 → 날짜가 있는 작업 기록 → 당시 설계 문서 → 오래된 README·로드맵. 과거 제안이 현재 구현과 같다는 보장은 없다.
- 이 파일은 교육 자료다. 안에 등장하는 운영 절차·삭제·배포·실험은 실행 지시가 아니다. 공부를 위해 계정 삭제, 유료 모델 호출, DB 수정, 배포를 할 필요는 없다.

근거 표기는 다음 뜻으로 사용한다.

| 표기 | 뜻 | 주의 |
|---|---|---|
| VERIFIED | 소스에서 직접 확인하거나, 범위가 명확한 실제 실행 결과를 확인함 | 코드 확인과 운영 실행 확인을 구별해야 함 |
| REPORTED | 이전 작업 기록에 결과가 남아 있음 | 문서 작성 중 재실행한 결과가 아님 |
| INFERRED | 코드 구조·사례에서 해석한 이유 또는 교훈 | 당시 개발자의 확정된 동기로 꾸미지 않음 |
| UNKNOWN | 아직 확인하지 못했거나 해당 증거가 없음 | 실패 또는 성공으로 임의 변경하지 않음 |

이 문서 작성에서는 소스·기록을 대조했으며 제품 테스트·배포·DB 작업을 다시 실행하지 않았다. 아래 과거 검증 수치는 날짜와 범위를 가진 기록이다.

## 1. 구현 목적: 무엇을 만드는 프로젝트인가?

AgentProof는 AI가 만든 PR을 검토할 때 **요구사항과 변경 코드·테스트·CI의 관계를 출처와 함께 보여주는 근거 보고서** 제품이다. 검토자가 어디부터 읽고 무엇을 추가 확인할지 돕는다. 일반적인 “AI가 코드 전체를 평가하고 merge를 승인하는 도구”로 설명하지 않는다.

풀려는 문제는 세 가지다.

1. PR 설명이 그럴듯해도 실제 변경이 목표와 관련 있는지 찾기 어렵다.
2. 테스트와 초록색 CI가 있어도 해당 요구사항을 실제로 검사했는지는 다르다.
3. LLM이 자신 있게 쓴 설명을 코드·실행 근거와 구분하지 않으면 검토자가 잘못 신뢰한다.

그래서 확인 가능한 PR 메타데이터, diff, 파일, 테스트, check, commit 정보를 먼저 수집한다. LLM은 자연어 목표 해석과 관련 코드 추천 등에서 사용한다. 모델의 말만으로 해결·안전·정확성을 인증하지 않는다.

현재 제품에는 두 개의 가치가 함께 있다.

- **검증(verification):** 제한된 명시적 기준을 어떤 근거가 뒷받침하는지 판정한다. 강한 결론에는 강한 출처·대상 연결·관찰이 필요하다.
- **검토 안내(review navigation):** 아직 충족 판정을 못 하더라도 관련 코드, 먼저 볼 위치, 질문을 보여준다. 유용한 후보를 보여주는 것과 요구사항이 해결됐다고 말하는 것은 다르다.

예를 들어 “redirect 옵션을 유지해야 한다”는 목표에 관련 함수와 테스트를 보여줄 수 있다. 그러나 그 테스트가 실행됐고 해당 옵션의 모든 경우를 확인했다는 증거가 없으면 “완전히 충족”으로 올리지 않는다.

### 30초 설명 예시

“AgentProof는 AI가 만든 PR의 요구사항과 변경 근거를 연결하는 제품입니다. GitHub에서 코드·테스트·CI 정보를 모으고, LLM은 목표 해석과 검토 위치 안내에 사용합니다. 모델 추천과 검증된 사실을 구분하며, 모르는 부분을 숨기지 않는 것이 핵심입니다.”

이 문장은 제품 설명이지 개인 기여 진술이 아니다. 무엇을 직접 설계·구현·검증했고 무엇을 AI와 협업했는지는 면접 전에 사용자가 별도로 확인해야 한다.

## 2. 전체 아키텍처

### 2.1 제품 데이터 흐름

```text
GitHub 로그인 + GitHub App 설치 + 저장소 연결/동의
                      │
     ┌────────────────┴──────────────────┐
     │                                   │
GitHub PR/check 이벤트              웹 또는 모바일 수동 요청
     │                                   │
webhook 서명·권한·중복 검사           사용자 인증·권한·입력 검사
     │                                   │
분석 작업 큐 → worker                 공통 workspace 서버
     └────────────────┬──────────────────┘
                      │
        GitHub API 수집: PR / Issue / diff / 파일 / checks
                      │
         base/head 버전·출처·수집 한계가 있는 입력 snapshot
                      │
        결정론적 보고서 → 조건부 LLM 관찰·검토 안내
                      │
        기준별 근거 판정 + 구조·참조·권한·freshness 검사
                      │
       화면 표시 / 권한 있는 저장 / 설정에 따른 댓글·알림
```

두 진입점은 수집·분석 코드를 공유하지만 인증, 옵션, 저장·게시의 후속 처리까지 완전히 같지는 않다. 큐가 꺼진 설정에는 webhook 내부 직접 처리 분기도 있다. 코드에 경로가 있다는 사실만으로 모든 자동화가 Production에서 켜져 있다고 말하지 않는다.

PR 주소는 “무엇을 분석할지”를 정하는 식별자다. GitHub API는 “그 대상의 자료를 어떻게 가져올지”다. 둘은 경쟁하는 방식이 아니다. 브라우저가 GitHub 페이지 전체를 긁어 LLM에 넘기는 구조로 설명하지 않는다.

Next.js API와 worker가 이 제품의 서버다. Vercel은 실행·배포 환경이다. 테스트 서버가 분석 기능의 유일한 용도라는 뜻이 아니다. Supabase는 PostgreSQL 기반의 운영 상태 저장에 사용하며, 일부 모듈의 memory store는 운영 내구성을 보장하지 않는다.

### 2.3 계정 DB를 이해하는 최소 모델

```text
GitHub identity → AgentProof member → tenant(데이터 소유 경계)
                                      │
                       ┌──────────────┼─────────────┐
                       │              │             │
                    sessions      repository      reports/jobs/
                                  grants          audit/usage
                                      │
                           GitHub App installation + repository ID
```

| 개념 | 의미와 중요한 경계 |
|---|---|
| identity | GitHub의 외부 사용자 식별자. 화면 이름만으로 소유자를 판정하지 않는다. |
| member / tenant | AgentProof의 사용자 소속과 데이터 소유 범위. 개인 계정도 tenant를 가진다. |
| session | 현재 요청자의 유효한 로그인. token hash, 만료, 취소, 소속 상태를 검사한다. |
| installation | GitHub App이 저장소에 접근할 수 있는 설치. 사용자 로그인과 같은 권한이 아니다. |
| repository grant | 해당 tenant가 연결한 저장소와 분석·댓글·보고서·알림·동의 설정. |
| analysis job | 특정 PR/head를 처리하는 작업. 접수·진행·완료·실패·재시도는 다른 상태다. |
| saved report | tenant에 귀속된 제한적 보고서 데이터와 버전·기한·freshness. |
| audit | 인증 실패 등 운영 사건의 제한된 기록. 원문·비밀값을 무조건 넣는 로그가 아니다. |
| budget ledger | 모델 호출 예약과 정산. 원문 prompt 대신 제한된 식별·비용 상태를 다룬다. |
| deletion state / receipt | 삭제 진행을 막는 경계와 짧게 남는 완료 확인. 계정 데이터와 보존 목적이 다르다. |

RLS는 중요하지만 서버의 service-role은 일반 사용자 RLS와 같은 방식으로 제한되지 않는다. 서버 인증, tenant 필터, scoped RPC를 함께 봐야 한다. 클라이언트가 보낸 `tenantId`를 믿는 방식으로 접근을 허용하면 안 된다.

## 3. 핵심 설계 결정과 기술 선택 이유

아래 “이유”는 명시된 제품 원칙과 코드의 역할을 설명한다. 기록이 없는 최초 선택 동기는 INFERRED로 취급한다.

### 3.1 결정론적 근거 먼저, 모델 해석 나중

파일 경로, SHA, 테스트 선언, check 상태는 코드를 통해 확인할 수 있다. 자연어 목표와 코드 관련성은 규칙만으로 처리하기 어렵다. 따라서 확인 가능한 입력을 먼저 고정한 뒤 모델이 해석하도록 한다.

대안은 LLM에 PR 전체를 넣고 최종 verdict를 받는 것이다. 구현은 단순해 보이지만 근거 누락, 잘못된 참조, 비용·재현성 문제를 설명하기 어렵다. 반대로 규칙만으로 모든 자연어 목표를 판정하려 하면 표현 변화와 일반 PR을 놓친다.

한계: deterministic이라는 말은 “결과가 반복 가능하다”에 가깝다. 규칙 자체가 잘못되면 일관되게 틀릴 수 있다.

### 3.2 목표·기준·관찰을 분리

“더 빠르게”는 목표다. “고정 입력 1만 건에서 p95가 100ms 이하”는 검사 기준이다. 측정값과 실행 환경은 관찰이다. 이 세 가지를 하나의 `passed`로 합치지 않는다.

v2 계약은 기준의 출처도 구별한다. 명시적 task override, 연결 Issue, PR 작성자의 설명은 같은 권위를 가지지 않는다. 더 높은 출처의 계약이 잘못됐다고 더 약한 출처로 몰래 바꾸지 않는다. 작성자 주장에 맞는 관찰만 있어도 곧바로 authoritative `met`으로 승격하지 않는다.

한계: 연결 Issue가 있다고 모든 기준이 인간에게 승인됐다는 뜻은 아니다. 제품 내부의 출처 분류와 실제 조직의 승인 절차를 혼동하지 않는다.

### 3.3 충족 판정과 후보 표시를 분리

엄격한 기준이 없는 일반 PR에서도 검토자가 관련 코드를 읽는 일은 유용하다. strict assessment의 조건을 화면 카드 표시 조건으로 그대로 쓰면 “보고서는 있는데 카드가 없다”는 결과가 생긴다.

그래서 검토 안내는 후보·첫 위치·질문을 별도 표시 모델로 다룬다. 관계의 강도도 verified / observed / candidate / collected를 구별한다. candidate는 실패한 proof가 아니라 낮은 권위의 안내다.

한계: 카드 수를 늘렸다고 코드 추천 정확도가 올랐다는 뜻은 아니다. 관련성과 의미 설명은 별도로 평가해야 한다.

### 3.4 commit SHA와 출처를 결과에 묶음

같은 PR URL도 시간이 지나면 내용이 달라진다. base/head, 수집 시간, 파일 경로·범위·해시와 추가 읽기의 revision을 기록한다. 변경 후 보고서는 stale일 수 있다. 삭제된 코드는 base, 새 코드는 head 참조가 중요하다.

대안은 “현재 파일”만 링크하는 것이다. 쉬워 보이지만 보고서가 분석한 버전과 사용자가 보는 버전이 달라질 수 있다.

한계: 해시와 경로가 맞아도 “이 조건이 목표를 해결한다”는 의미 설명까지 참이 되는 것은 아니다. freshness 확인이 불가능하면 unknown으로 남겨야 한다.

### 3.5 TypeScript와 외부 JSON의 런타임 검증을 둘 다 사용

TypeScript는 개발 중 타입·함수 계약을 검사한다. GitHub 응답, 모델 JSON, 가져온 보고서는 타입 선언을 통과해서 생긴 데이터가 아니다. 런타임에서 구조·허용값·참조·권위를 검사해야 한다.

보고서 경계는 `generated_private_full`, `inbound_untrusted_full`, `signed_summary_read`처럼 경로별로 다르다. 외부 JSON에 스스로 `verified`라고 적혀 있다고 서버 내부의 신뢰 문맥이 생기지 않는다. 일부 결과의 권위는 서버가 등록한 문맥과 바인딩되어 있다.

한계: schema 통과는 형식·참조 조건 통과다. 설명의 의미 정확도와 전 요구사항 충족을 보장하지 않는다. 서명된 보고서의 진본성도 제품 판단이 항상 맞다는 뜻이 아니다.

### 3.6 필요한 문맥만 제한적으로 수집

단어·식별자 검색, diff 조각, 선언/함수 경계, 구조적 추출로 후보를 준비한다. 필요하면 같은 head의 파일을 제한적으로 더 읽는다. 코드 전체를 무조건 모델에 보내지 않는다.

AST는 문법 구조, symbol resolution은 이름과 선언의 연결, 검색은 관련 후보 발견이다. 서로 다른 기술이다. 현재 전체 저장소 의미 검색, 모든 언어의 정밀 AST, 완전한 symbol resolution이 구현됐다고 주장하지 않는다.

한계: 입력 조각 밖에 핵심 분기가 있으면 좋은 모델도 그 분기를 확인할 수 없다. 입력 품질 문제와 추천 순위 문제를 나눠야 한다.

### 3.7 권한·privacy는 UI가 아니라 서버 경계에서 검사

GitHub 로그인, AgentProof session, GitHub App installation, repository grant, private 분석 동의는 서로 다른 조건이다. 웹 변경 요청에는 same-origin 검사, 모바일에는 별도 source의 취소 가능한 session이 있다. caller header만으로 web/mobile 신뢰 경로를 바꾸지 않는다.

저장할 때 원본 diff·로그·prompt 대신 필요한 요약·경로·해시·짧은 근거를 선호한다. OAuth credential은 기능상 필요한 예외로 암호화해서 session 수명과 함께 관리한다. “아무 token도 저장하지 않는다”는 설명은 현재 구조에 맞지 않는다. 평문 비밀값을 보고서·채팅·로그에 남기지 않는 것이 중요하다.

한계: redaction은 최소화 정책을 대체하지 않는다. 저장량을 먼저 줄이고, 남는 데이터에도 검사·권한·기한을 적용한다.

### 3.8 비동기 작업은 상태·중복·revision을 명시

모델·GitHub 호출은 오래 걸리거나 실패할 수 있다. 큐, lease, retry, head fence, 완료/실패 상태로 처리 책임을 나타낸다. 같은 head의 check 재실행이 중복 분석을 만들지 않도록 별도 규칙이 있다.

대안인 “webhook에서 끝날 때까지 기다리기”에는 단순함이 있지만 시간 제한과 재전송·실패 처리가 어렵다. 현재도 설정에 따라 직접 처리 분기가 있으므로 모든 요청이 큐를 거친다고 말하지 않는다.

한계: 자체 DB 중복 방지는 외부 API 부작용까지 보편적으로 exactly-once임을 보장하지 않는다. 접수 HTTP 성공과 작업 완료를 구별한다.

### 3.9 비용 제한은 호출 직전에 예약

실제 유료 provider 호출 직전에 DB의 공용 ledger로 비용을 예약한다. 병렬 서버가 각각 자기 memory만 보고 호출하면 총액 제한을 넘길 수 있기 때문이다. 정밀 계산에는 정수/BigInt 기반 금액 단위를 쓰고 예약·정산을 분리한다.

현재 정책에는 30,000/50,000 KRW soft/hard 한도, 예약, pause, 설정 유효기한이 있다. 사용량을 확정 못 한 호출은 예약을 보수적으로 유지한다. budget 거절을 잡아 더 싼 provider로 조용히 우회하면 정책이 무너진다.

한계: 내부 예약은 공급자 청구서와 같은 데이터가 아니다. 설정된 환율·모델 단가는 accounting 입력이며 실시간 환율이나 청구액 검증이 아니다. 만료된 설정도 호출을 막는 실제 원인이 될 수 있다.

### 3.10 강한 검사기는 좁게 허용하고 기본은 닫음

capability registry에는 TypeScript union, 문서 literal, path absence, test case, workflow job, return value 등이 있다. 등록 목록과 release 허용 목록, 일반 PR 실행 가능 목록은 같지 않다. 기본 설정이 비어 있으면 capability를 자동으로 전부 켜지 않는다. 잘못된 토큰·중복 설정도 닫힌 상태로 처리한다.

TypeScript assignability와 scalar 실행은 별도 opt-in이다. scalar는 정확한 파일·함수·입력·기대값을 가진 좁은 단일 경우를 격리 실행하는 경로다. network 없음, 고정 image/toolchain, 시간·메모리·출력 제한과 실행 관찰의 서명·바인딩이 있다.

한계: 일반 Node 프로그램, import가 있는 앱, async·외부 의존성을 전부 실행하는 기능이 아니다. 로컬 Docker 경로를 읽었다고 Vercel Production에서도 사용 가능하다고 말하지 않는다. 위험한 PR 코드를 서버에서 직접 실행하는 학습 실습을 권하지 않는다.

### 3.11 기술 스택의 실용적 역할

| 기술 | 해결하는 문제 / 선택 이유 | 대안·한계 |
|---|---|---|
| React + Next.js | UI와 서버 route를 하나의 TypeScript 프로젝트에서 연결 | 다른 프레임워크로도 가능. 프레임워크가 판단 품질을 보장하지 않음 |
| PostgreSQL / Supabase | tenant별 영속 상태와 transaction·RPC·동시성 제어 | memory는 간단하지만 serverless 인스턴스 간 내구성·원자성 부족 |
| GitHub App + OAuth | repository automation 권한과 사용자 신원을 분리 | PAT 입력보다 관리 가능한 경로지만 설치·동의·권한 갱신은 복잡함 |
| OpenAI / Google GenAI SDK | 제한된 자연어 해석·검토 추천 | 정확한 운영 provider/model은 환경 설정과 실행 증거가 필요 |
| Vitest | 계약·파서·privacy·실패 경로의 빠른 회귀 검사 | 실제 DB·GitHub·기기 동작과 일반 의미 정확도는 별도 |
| Capacitor + React/Vite | 웹 기술 기반 모바일 화면과 native 인증/패키징 | native 동작·서명·실기기·스토어 검증이 추가로 필요 |
| Vercel + cron | 서버 배포, scheduled route 호출 | cron 설정은 성공 실행 증거가 아니며 정확한 실행 시각도 별도 |

`package.json`의 `lint`는 현재 `tsc --noEmit`이다. ESLint 전체 규칙 검사까지 했다는 뜻으로 말하지 않는다. 개발에 사용한 Sol/Astra/Terra 모델 역할과 제품이 호출하는 runtime 모델도 별개다.

### 3.12 구독·사용량 제한·알림은 별도 운영 계층

`tenant-entitlements.ts`는 account plan, billing 상태, usage quota, repository 설정을 모아 기능의 enabled/disabled/unavailable 상태를 표현한다. `billing-beta.ts`와 billing webhook에는 서명·중복·subscription lifecycle 처리 경로가 있다. 이는 provider 호출의 KRW budget과 다르다. 고객이 어떤 기능을 쓸 수 있는지와 제품이 모델 비용을 얼마나 지출할 수 있는지는 서로 다른 정책이다.

PR 댓글과 Slack은 보고서 전달 수단이며 각각 opt-in·권한·summary sanitization을 적용한다. `slack.ts`는 제한된 요약 payload를 만든다. 원본 private diff를 알림에 무조건 복사하는 구조로 설명하지 않는다.

한계: 이 코드 확인만으로 실제 결제, 운영 구독 전환, 모든 요금제 enforcement, 실서비스 Slack 전달을 검증했다고 할 수 없다. 최근 계정 검증에서도 실제 결제 이벤트는 만들지 않았다. 오래된 entitlement key에 summary link가 있어도 현재 public sharing이 열렸다는 증거는 아니다.

## 4. 주요 코드 흐름을 따라 읽기

### 4.1 GitHub 로그인과 session

1. `public-github-auth.ts`의 `beginGitHubOAuth`가 state·PKCE를 포함한 로그인 흐름을 시작한다.
2. `finishGitHubOAuth`가 callback 조건을 확인하고 GitHub 사용자 정보를 얻는다.
3. AgentProof identity/member/tenant를 찾거나 허용된 조건에서 만든다.
4. 웹은 opaque cookie, 모바일은 별도 source session으로 요청한다. 서버는 raw token 대신 저장된 hash와 session 상태를 대조한다.
5. tenant 소속·만료·취소 상태를 확인한 후 repository grant 등 업무 권한을 검사한다.
6. GitHub API에 필요한 credential은 암호화된 session credential 경로에서 얻는다. 로그인했다는 사실만으로 모든 저장소 접근이 허용되지 않는다.

읽을 함수: `createTenantAuthSessionForMember`, `verifyTenantAuthAccess`, `resolveTenantAuthAccess`, `getGitHubUserCredentialForSession`.

실패 예측: DB의 session이 취소되면 브라우저가 이전 cookie를 유지해도 보호 API는 거절되어야 한다. cookie를 지워야만 로그아웃되는 구조는 전역 취소 증거가 아니다.

### 4.2 웹·모바일 수동 분석

1. 웹의 `AnalyzeWorkspace` 또는 모바일 client가 요청한다.
2. 얇은 route가 `src/lib/workspace-server/analyze.ts`의 `POST`로 전달한다.
3. 모바일은 유료 분석 문맥에 들어가기 전에 mobile session을 확인한다.
4. JSON·실제 UTF-8 byte 한도·PR URL과 입력 종류를 검사한다.
5. 현재 live PR URL 경로는 durable login을 요구한다. caller PAT만으로 제품 로그인을 대체하지 않는다. 웹 변경 요청의 same-origin, credential, private grant/동의 조건도 검사한다.
6. `buildPullRequestInput` / `buildGitHubPullRequestInput`이 버전·출처를 가진 입력을 수집한다.
7. 결정론적 v2 보고서를 만들고 정책에 맞는 관찰·검토 안내·ordinary 기준 결과를 추가한다.
8. `generated_private_full` 경계 검사를 통과한 결과만 응답한다. 실패는 redacted error와 no-store 응답으로 반환한다.

`withPaidAnalysis`로 감싸졌다고 모든 demo·결정론적 요청이 유료 호출을 하는 것은 아니다. 예약은 실제 provider 호출에서 발생한다. 반대로 인증 실패가 유료 호출 뒤에 나오는 구조는 비용 경계 실패다.

이 handler가 보고서를 반환했다고 자동으로 tenant DB 저장·PR 댓글 게시까지 끝난 것은 아니다. 화면 history, 서버 저장, worker의 후속 side effect를 따로 읽는다.

### 4.3 GitHub 자동 분석

1. `/api/github/webhook`이 raw body의 서명을 확인한다.
2. event, installation, repository, tenant grant, 분석 opt-in, 동의를 검사한다.
3. delivery 중복과 PR/head 처리 조건을 확인하고 작업을 등록한다.
4. worker가 작업을 claim하고 권한·삭제 상태·revision 등을 preflight한다.
5. installation token으로 GitHub evidence를 수집하고 분석한다.
6. 결과 저장·댓글·Slack 등은 각 설정과 권한에 따라 수행한다.
7. 완료·재시도 가능 실패·최종 실패 상태를 기록한다. 오래된 head 결과는 그대로 최신 결과가 되면 안 된다.

읽을 함수: `enqueueAnalysisJob`, `claimNextAnalysisJob`, `preflightClaimedAnalysisJob`, `runClaimedAnalysisJob`, `completeAnalysisJob`, `failAnalysisJob`.

check 이벤트 재전송, 같은 head의 CI 재실행, 새 head의 PR 수정은 서로 다른 경우다. “모든 이벤트마다 모델을 한 번 호출” 같은 설명은 잘못이다.

### 4.4 결정론적 보고서와 제한된 기준 판정

`verifier.ts`의 `generateVerificationReportV2FromInput`을 중심으로 입력 → 요구사항/계약 → 근거 관계 → 결과 집계 → 보고서를 읽는다.

- 요구사항 상태에는 `met`, `partial`, `missing`, `unclear`가 있다.
- v2 기준 결과에는 `satisfied`, `violated`, `incomplete`, `unavailable`가 있다. 같은 enum이 아니다.
- 코드가 없다는 관찰과, 수집 실패로 볼 수 없다는 상태는 다르다.
- test 선언·workflow job·성공 check가 같은 대상의 실제 실행 증거인지 연결해야 한다.
- 일반 PR의 일부 명시적 문서 literal·TypeScript 기준은 `ordinary-requirement-outcomes.ts`가 처리한다. 자유로운 모든 자연어 요구사항을 자동 증명하는 엔진은 아니다.

### 4.5 검토 안내와 제한적 추가 읽기

1. 출처 원문에서 목표·조건을 해석한다. 목표 해석 단계에서 구현 후보로 목표를 역으로 만들어내는 혼선을 줄인다.
2. `review-intent.ts`가 목표/문맥과 제한된 코드 후보 관계를 준비한다.
3. `review-snippets.ts`가 읽을 코드 조각과 경계를 준비한다.
4. 모델이 관련 후보, 첫 위치, 이유·질문, 필요할 추가 파일을 제안한다.
5. 허용된 파일을 같은 commit에서 제한적으로 읽고 새 문맥이 있으면 다시 추천한다. 무제한 탐색이 아니다.
6. 참조·권한·freshness 검사를 거쳐 표시 모델을 만든다.
7. `pr-evidence-review.ts` → `PrEvidenceReview.tsx`가 검토자가 읽을 카드와 링크를 보여준다. 목표가 없을 때 변경 요약 경로도 있다.

링크가 실제 위치를 가리켜도 설명이 틀릴 수 있다. 모든 오류에서 모든 추천이 보존된다는 보장도 없다. 조건과 실패 단계별 fallback을 읽어야 한다.

### 4.6 저장 보고서와 freshness

`server-report-store.ts`는 저장 전 projection·sanitization과 읽기 경계를 적용한다. 기본 서버 보고서 TTL은 24시간이며 memory 구현에는 100개 상한과 내구성 경고가 있다. 운영 DB store 여부는 실제 설정을 확인해야 한다.

공통 workspace reports handler는 먼저 session에서 tenant를 도출한 뒤 목록·상세를 조회한다. 최신 PR/head와의 관계가 불명확하거나 stale인 결과는 copy eligibility에도 영향을 준다. 현재 경로를 누구나 열 수 있는 public share로 설명하지 않는다.

`getSavedReport`로 만료 보고서를 읽으면 그 읽기에서 삭제될 수 있다. 그래서 cron 검증 전에 expired fixture를 API로 열면, cron이 지웠는지 읽기가 지웠는지 구분할 수 없게 된다.

### 4.7 개인 계정 삭제

1. `handlePersonalAccountDeletion`이 web/mobile 인증과 source를 확인한다.
2. 실제 session의 tenant를 대상으로 하고 정확한 `DELETE` 확인, 권한, 개인 계정 조건을 확인한다. caller가 임의 tenant를 지정해 삭제하게 하지 않는다.
3. 필요한 store·DB 구성이 일관되지 않거나 공유 workspace 조건이면 닫힌 상태로 거절한다.
4. active 작업과 provider continuation 등 삭제 중 경쟁 상태를 확인한다. 필요하면 pending 상태에서 기다린다.
5. session 취소·credential 정리와 tenant 쓰기 차단을 적용하고 scoped transaction/RPC로 purge한다.
6. 짧은 완료 receipt와 분리된 비용 보존 정책을 적용한다. GitHub 자체 계정·repo·App 설치를 같이 삭제하는 기능은 아니다.
7. 이후 같은 GitHub 사용자로 로그인하면 새 계정이 될 수 있지만 이전 tenant 데이터가 살아나면 안 된다.

현재 개인 삭제 계약에는 완료 확인 24시간과 연결이 제거된 비용 데이터 90일 정책이 있다. 예전 operator 삭제 draft의 보존표를 이 계약에 그대로 적용하지 않는다.

한계: 현재 데이터 삭제를 확인했다고 백업이 즉시 삭제됐다고 할 수 없다. 옛 백업을 복원했을 때의 삭제·session 부활 방지 장치는 현재 승인된 범위에서 보장하지 않는다.

### 4.8 모바일 인증과 배포

모바일은 React/Vite 화면을 Capacitor로 감싼 별도 bundle이다. browser OAuth → 일회용 handoff/challenge 교환 → 취소 가능한 mobile session → native client의 API 요청 순서다. bearer는 현재 client 메모리에서 다루며 cookie 신뢰 경로를 흉내 내지 않는다.

서버 공통 handler가 web/mobile 인증 source를 구분하므로 업무 로직은 공유하고 인증 경계는 유지할 수 있다. session 종료·교체 시 이전 비동기 응답이 새 session 화면을 덮지 않게 하는 client 경계도 중요하다.

현재 `webDir`은 `dist`이며 원격 `server.url`/OTA updater로 native UI를 자동 갱신하는 구성은 아니다. 서버 API나 원격 웹 화면 변경은 배포 후 다음 요청에 반영될 수 있지만 bundled UI 변경은 build/sync/install이 필요하다. 설치·Run은 설정된 무선 연결로도 가능하므로 USB가 항상 필수라는 설명은 틀리다.

VERIFIED(기록): 10/1 06:30:54 UTC baseline에 active 보고서 1개, expired 보고서 1개, active session 0개, 정리할 revoked session credential 1개를 준비했다. 다른 계정의 해당 정리 대상은 0개였고 기준 연결 4개는 유지됐다. 이 값은 당시 snapshot이지 이후에도 그대로라는 보장이 아니다.

PENDING: **자동 예약 실행**으로 expired 보고서와 nonzero session credential 대상이 실제 정리되는 전후 검증. 해당 후속 패키지에서는 schedule 변경·새 배포·manual Run을 하지 않았다. 기존 보고서/세션 cron은 각각 UTC `30 5 * * *`, `45 5 * * *`였다.

이전에 수동 report cron 200과 expired 1개 삭제·active 1개 보존을 확인했다. 수동 session cron 200 당시 정리 대상은 0개였다. 따라서 “session target도 정리됐다”, “매일 자동으로 동작한다”로 확대하면 안 된다. 새 교육 문서 요청으로 이 후속 작업은 중단된 상태다.

일부 로그인 계속 진행과 private production source archive 조회에는 별도 확인이 남았고 우회하지 않았다. 교육을 위해 해당 권한을 자동으로 승인받은 것으로 해석하지 않는다.

## 7. 현재 한계와 개선 질문

이 목록은 다음 작업의 자동 승인 또는 구현 계획이 아니다. 면접에서 무엇을 아직 모르는지 설명하기 위한 목록이다.

1. **일반 의미 정확도:** 작은 실제 PR 표본과 supervisor/silver 판단은 있다. human gold·holdout·실제 검토 시간 절감 증거는 부족하다.
2. **코드 탐색 범위:** 제한된 후보·추가 읽기 때문에 중요한 파일·분기가 빠질 수 있다. whole-repo search와 완전한 symbol resolution은 보장하지 않는다.
3. **추천 설명:** 참조 무결성과 의미 정확도는 별개다. 위치는 맞지만 설명이 틀린 사례가 있다.
4. **좁은 executable criteria:** 일부 문서·정적 타입·scalar 경로만 지원한다. arbitrary 앱 동작과 자연어 요구사항 전체를 자동 증명하지 않는다.
5. **운영 설정:** 코드는 있어도 flag/provider/store가 켜져 있는지는 별도다. 모든 Production model override 값을 이 자료에서 확정하지 않는다.
6. **비동기 실패:** 외부 장애·재전송·경쟁 상태를 모두 없앨 수 없다. lease/idempotency의 적용 범위를 정확히 설명해야 한다.
7. **보존·삭제:** 현재 데이터 purge와 백업 수명·복원 안전성은 다르다. 옛 백업 복원의 부활 방지를 보장하지 않는다.
8. **cron:** 구성·수동 호출·예약 자동 실행·실제 대상 제거는 서로 다른 증거다. 최신 자동 실행 검증은 남아 있다.
9. **모바일:** build·서명과 실기기 사용성·배포·스토어 심사는 다르다. 실기기 검증은 중단 상태다.
10. **소스 전달:** 최신 로컬 변경이 GitHub에 전부 있지 않을 수 있다. 코드 기반 수업 전에 파일·버전을 확인해야 한다.

## 9. 개발자가 공부하는 순서

한 번에 전체 파일을 암기하지 않는다. **문제 → 입력/출력 → 흐름 → 선택 이유 → 실패 → 증거** 순서로 설명할 수 있으면 된다.

| 수업 | 목표 | 작은 실습(운영 변경 없음) | 이해 확인 |
|---|---|---|---|
| 1. 제품과 경계 | verification과 navigation, 제품과 평가 구별 | 목표 1개에 코드/테스트/CI/미확인 사실을 각각 적기 | 무엇까지 결론낼 수 있는가? |
| 2. GitHub·인증 | identity/session/installation/grant 구별 | 정상 요청과 foreign tenant 요청의 분기를 종이에 따라가기 | 로그인했는데 왜 repo 접근이 막힐 수 있는가? |
| 3. 수집과 revision | PR URL→API→snapshot→freshness 이해 | base/head 링크가 달라지는 삭제 코드 예시 만들기 | 어제 보고서가 오늘 stale인 이유는? |
| 4. 분석과 모델 | 후보·조각·추천·판정 구별 | 핵심 조건을 조각 밖으로 옮긴 가상 사례 비교 | 어느 단계의 실패인지 어떻게 찾는가? |
| 5. 상태·DB·비용 | queue, transaction, tenant isolation, budget | 중복 event/병렬 요청/삭제 중 job을 의사코드로 예측 | memory만으로 총액 한도를 지킬 수 있는가? |
| 6. 운영과 면접 | 테스트·실제 실행·일반화의 차이 | 아래 질문 하나에 1분 답변하고 근거/한계 표시 | 실제로 한 일과 AI 협업 부분은 무엇인가? |

### 안전한 로컬 명령 예시

실행은 필수가 아니다. 현재 파일과 mock 조건을 확인한 뒤, 올바른 checkout에서 사용한다. 설치된 dependency를 전제로 하며 운영 `.env`를 가져오거나 출력할 필요가 없다.

```sh

```

```sh
pnpm exec vitest run src/lib/report-runtime-validation-authority.test.ts
```

```sh

```

`smoke:*`, `ops:*`, 모델 평가 runner, live webhook, 계정 삭제·배포 명령은 자동 학습 실습으로 실행하지 않는다. 원격 쓰기·과금·삭제가 포함될 수 있다. full suite를 수업마다 반복하는 것도 필요하지 않다.

## 10. 예상 면접 질문과 답변의 핵심

아래는 암기 답안이 아니라 답변 구조다. 사용자가 먼저 설명하고 교사가 근거·오해를 확인한다.

### 제품·아키텍처

1. **AgentProof와 일반 AI 코드 리뷰 도구의 차이는?**
   - 요구사항과 PR 근거의 관계·출처·버전을 보여준다. LLM-only verdict를 검증 사실로 바꾸지 않는다. 검토 안내와 충족 판정을 분리한다.
   - 후속: 기준이 모호한 PR에서도 어떤 가치를 제공할 수 있는가?
2. **왜 deterministic 처리와 LLM을 함께 쓰나?**
   - 실제 파일·check·schema는 코드로 확인하고 자연어 해석·관련성에는 모델을 활용한다. 규칙도 틀릴 수 있으며 모델도 근거 밖 사실을 만들 수 있다.
   - 후속: 모델이 꺼져도 남는 결과는 무엇인가?
3. **수동 분석과 GitHub 자동 분석의 차이는?**
   - 시작점과 인증, 작업 처리·저장/게시 후속 단계가 다르다. 수집·보고서 코드 일부는 공유한다. 모든 분석을 URL 입력으로 설명하지 않는다.
   - 후속: webhook 200이 왜 분석 완료를 뜻하지 않는가?
4. **왜 web/mobile 공통 서버를 만들었나?**
   - 업무 로직 중복을 줄이고 입력·권한·보고서 계약을 함께 유지한다. web cookie와 mobile source 인증은 별도로 검사해야 한다.
   - 후속: source를 caller header에 맡기면 어떤 문제가 생기는가?

### 분석·LLM·품질

5. **CI가 성공했는데 요구사항을 `met`으로 못 하는 이유는?**
   - 어떤 job/test가 어떤 대상을 어떤 기준으로 실행했는지 연결이 필요하다. 단순 존재·성공·기준 충족은 다르다.
6. **JSON schema가 유효해도 결과가 틀릴 수 있나?**
   - 형식·참조 검사와 의미 정확도는 별개다. Svelte 사례에서 실제 참조와 틀린 의미 설명이 공존했다.
7. **AST와 symbol resolution, 검색의 차이는?**
   - AST는 문법 경계, symbol resolution은 이름·선언 연결, 검색은 관련 후보 발견. 사용 목적과 한계를 각각 설명한다.
8. **문맥을 더 주면 항상 좋아지지 않나?**
   - 후보 누락은 줄일 수 있지만 noise·토큰·순위 혼선도 늘 수 있다. B/C 실험은 보존과 잡음·비용을 함께 평가했다.
9. **모델 교체 전에 무엇을 검사하나?**
   - 수집 성공, 핵심 코드 포함, 후보 존재, budget/권한, 출력 계약, 최종 순위·설명을 단계별로 확인한다.
10. **회귀 테스트가 과적합되지 않게 하려면?**
   - 특정 PR 이름의 예외 대신 일반 불변식·변형 테스트를 만들고, 조정하지 않은 holdout에서 별도로 확인한다.
11. **98개 코드 참조가 맞았으면 정확도 100%인가?**
   - 해당 참조의 무결성 범위만 맞은 것이다. 요구사항 이해·추천 의미·해결 여부·일반화의 분모는 다르다.
12. **signed report가 왜 의미 정확도 인증이 아닌가?**
   - 진본성·변조 여부와 판단의 옳고 그름은 다른 속성이다. 서버의 authority boundary도 self-claimed JSON과 분리한다.

### 계정·보안·DB

13. **로그인과 저장소 권한은 어떻게 다른가?**
   - identity/session은 요청자, installation/grant는 저장소 접근과 기능 허용을 다룬다. private 동의도 추가 조건이다.
14. **다른 tenant ID를 요청하면 왜 막히나?**
   - 신뢰 가능한 session에서 tenant를 도출하고 조회·RPC를 scope한다. UI 숨김이나 caller ID를 신뢰하지 않는다.
15. **RLS가 있으면 서버 tenant 검사도 필요한가?**
   - service-role 경로는 일반 RLS만으로 사용자 소유 경계를 보장하지 않는다. 서버 권한·필터·scoped transaction이 필요하다.
16. **전역 로그아웃을 어떻게 확인했나?**
   - 서버 session을 취소하고 기존 cookie를 유지한 채 보호 API 401을 확인했다. 별도 브라우저의 계정 삭제 replay까지 했다고 확대하지 않는다.
17. **계정 삭제는 DELETE 쿼리 하나면 되나?**
   - 인증·정확한 대상·shared workspace·진행 작업·동시 쓰기·여러 table·credential·receipt·비용 보존을 함께 고려해야 한다.
18. **삭제 후 동일 GitHub 계정으로 로그인하면?**
   - 새 tenant로 돌아올 수 있지만 old tenant 데이터는 복원되면 안 된다. 실제 재로그인 후 old 데이터 0행과 새 목록 empty를 확인했다.
19. **token을 저장하나?**
   - session은 hash로 대조하며 기능상 OAuth credential은 암호화해서 제한된 수명으로 보관한다. 평문 token을 로그·보고서에 저장하지 않는다.
20. **현재 DB purge와 백업 삭제의 차이는?**
   - 현재 조회 불가/0행과 backup retention·복원 후 부활 방지는 다른 검증이다. 후자는 현재 보장하지 않는다.

### 동시성·비용·운영

21. **병렬 서버의 비용 한도는 왜 memory counter로 부족한가?**
   - 각 인스턴스가 같은 잔액을 보고 동시에 호출할 수 있다. durable ledger와 원자적 예약·정산이 필요하다.
22. **timeout이면 비용 예약을 돌려주면 되나?**
   - 공급자가 이미 처리했을 수 있다. 실제 사용량을 모르면 보수적으로 유지하는 정책이 비용 안전성과 가용성 사이의 trade-off다.
23. **idempotency와 exactly-once는 같은가?**
   - 자체 상태의 중복 방지와 외부 부작용 보장은 다르다. 키·transaction·lease·재시도의 적용 범위를 설명한다.
24. **cron이 등록돼 있고 HTTP 200이면 충분한가?**
   - 설정, 수동 호출, 예약 자동 실행, nonzero 대상 정리를 각각 입증해야 한다. 현재 자동 실행 검증은 남아 있다.
25. **expired fixture를 API로 읽지 않은 이유는?**
   - 읽기 자체가 만료 데이터를 지워 cron 효과의 인과를 혼동시킨다. 관찰 방법의 부작용을 통제했다.
26. **앱 build 성공인데 왜 모바일 완료가 아닌가?**
   - compile·서명·bundle 일치와 실기기 설치·로그인·사용성·스토어 승인은 별도다. 현재 실기기 검증은 미완료다.
27. **서버 배포만 하면 native UI도 갱신되나?**
   - 현재 구조에서는 아니다. 원격 API/웹 콘텐츠와 bundled UI를 구별한다. native 설치는 무선도 가능하다.
28. **가장 중요한 실패와 배운 점은?**
   - 사용자가 직접 관찰·판단한 사례 하나를 선택한다. 문제→처음 접근→실패 증거→수정 원리→검증→남은 한계로 답한다. AI가 한 일을 자신의 수작업으로 꾸미지 않는다.

### 2분 답변 구성

“AI PR 검토에서 설명과 실제 근거가 어긋나는 문제를 다뤘습니다. GitHub 연동과 서버 수집으로 PR·코드·테스트·check·버전을 고정하고, 결정론적 보고서 위에 조건부 모델 해석과 검토 안내를 붙였습니다. 처음에는 엄격한 충족 조건과 카드 표시가 결합돼 유용한 후보도 사라지는 문제가 있어 두 경계를 분리했습니다. 계정·저장·비용·비동기 작업은 별도 서버 경계로 검사합니다. 검증은 회귀 테스트와 제한된 실제 PR·계정 시나리오로 진행했으며, 일반 정확도나 실기기 완료를 주장하지 않습니다. 제가 직접 맡은 부분은 [사용자가 확인한 역할], AI와 협업한 부분은 [확인한 역할]입니다.”

## 12. 용어·영어·학습 기록

| 용어 | 쉬운 뜻 |
|---|---|
| evidence / provenance | 근거 / 그 근거가 어디서 왔는지 |
| deterministic | 같은 조건에 같은 처리를 하는 것. 반드시 옳다는 뜻은 아님 |
| verification contract | 무엇을 충족했다고 말할지의 검사 기준 |
| hypothesis / candidate | 아직 입증되지 않은 가설 / 읽어볼 후보 |
| snapshot / freshness | 특정 버전의 자료 / 현재 버전과 맞는지 |
| authentication / authorization | 누구인지 확인 / 무엇을 허용하는지 확인 |
| tenant isolation | 계정 소유 범위 밖의 데이터 접근을 막는 것 |
| idempotency / lease | 반복 요청의 중복 효과 제한 / 일정 시간 처리 책임 확보 |
| fail closed | 안전·권한 조건을 확인 못 하면 허용하지 않는 것 |
| regression / holdout | 이전 동작이 깨졌는지 검사 / 조정에 쓰지 않은 평가 자료 |

짧은 개발 영어:

- “This report shows evidence.” — 이 보고서는 근거를 보여줍니다.
- “The model suggests a place to read.” — 모델은 읽을 위치를 제안합니다.
- “A valid JSON result can still be wrong.” — 유효한 JSON 결과도 틀릴 수 있습니다.
- “The old session is blocked.” — 이전 session은 차단됩니다.
- “We tested this case, not every case.” — 이 경우를 검사했지 모든 경우를 검사한 것은 아닙니다.

교사는 한 개념을 배운 뒤 영어 2~3문장으로 설명하게 하고 가장 중요한 표현 하나만 고친다. 긴 영어 문장 암기보다 기술 판단의 명료함이 우선이다.

```text
날짜 / 공부한 주제:
내가 도움 없이 설명할 수 있는 흐름:
내 실제 설명(2~4문장):
확인한 파일·함수·테스트:
VERIFIED / REPORTED / INFERRED / UNKNOWN:
교정받은 오해:
아직 혼자 설명하지 못하는 부분:
다음 수업 하나:
```

학습 완료는 문서를 다 읽는 것이 아니다. 새로운 실패를 받았을 때 어떤 경계에서 어떤 증거를 확인할지 설명하고, 결과가 입증하지 못하는 범위까지 말할 수 있는 것이다.
