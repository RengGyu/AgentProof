# AgentProof 제품 구조와 기술 지도 — 수정본

수정 기준: 2026-09-21. `codex/recover-bounded-target-20260913`의 HEAD `639cba137dc96652c5abd052ee4a1d187429acda`와 미커밋 변경을 포함한 로컬 소스의 진입점·수집·분석·표시를 대조했다. 이번에는 배포·라이브 실행을 하지 않았으므로 운영 가동 여부를 인증하지 않는다. 이전 판보다 이 수정본을 우선한다.

## 1. 제품을 한 문장으로 설명하기

AgentProof는 PR 검토자가 목표와 관련된 코드·테스트·실행 관찰을 찾아 읽도록 돕는 근거 보고서 제품이다. 어디를 먼저 보고 어떤 질문을 확인해야 하는지 안내한다. LLM 추천을 요구사항 해결, 코드 정확성, 보안 또는 merge 가능성의 증명으로 바꾸지 않는다.

Issue에서 가져온 목표와 PR 작성자의 설명은 출처를 구분한다. 현재 수집기는 PR 본문의 Issue 참조를 해석해 연결 원문을 수집하는 경로를 갖는다. 모든 관련 Issue를 자동 발견하거나 메인테이너 승인을 확인한다는 뜻은 아니다. Issue 없이 PR 설명으로 목표를 제안할 수도 있다. 목표를 확보하지 못하면 표시 모델에 변경 요약 경로가 있다. 설명 부족 자체를 미완성 판정으로 바꾸는 것이 제품 목적은 아니다.

## 2. 실제 제품 흐름: GitHub 연동과 자동 분석

```text
사용자: GitHub 로그인·앱 설치·저장소 연결/설정
  → GitHub가 PR 이벤트를 AgentProof webhook에 전달
  → 서버가 서명·대상·권한·처리 조건 확인
  → 분석 작업 등록 → worker 처리 (큐 활성화 시)
  → GitHub API로 PR·변경 파일·Issue·check 등 수집
  → 근거 정리 + 조건에 맞는 LLM 목표 해석·코드 추천
  → 출처·참조·버전 및 보고서 검사
  → 설정·권한에 따라 저장 보고서 / PR 댓글 / 알림 전달
  → 사용자가 보고서에서 관련 위치·원문·check 링크 확인
```

이것은 코드에 존재하는 경로의 요약이다. 큐를 사용하지 않을 때 webhook 안에서 직접 분석하는 분기도 있다. 모든 이벤트가 분석되거나 결과가 자동 게시되는 것은 아니다. 자동화 설정·권한·배포 환경·저장소 공개 여부·분석 정책에 따라 달라진다. 코드 존재만으로 현재 Production에서 모두 켜져 있다고 말하지 않는다.

근거: `src/app/page.tsx`, `src/components/PublicGitHubEntry.tsx`, `src/components/PublicGitHubDashboard.tsx`, `src/app/api/github/webhook/route.ts`, `src/lib/analysis-worker.ts`.

### 자동 분석·수동 분석·평가는 서로 다른 진입 경로

| 경로 | 시작 계기 | 제품에서의 위치 |
|---|---|---|
| GitHub 연동 자동 분석 | GitHub가 PR 이벤트를 보냄 | 매번 PR 주소를 입력할 필요 없는 자동화 경로 |
| 수동 분석 화면 `/analyze` | 사용자가 PR 주소 등을 제출 | 실제 존재하는 별도 화면. 테스트 전용이라고 단정하면 안 됨 |
| 개발·평가 스크립트 | 개발자가 분석 API를 호출하거나 fixture로 실행 | 제품을 확인하는 도구. 이것으로 전체 사용자 흐름을 정의하면 안 됨 |

**PR 주소와 GitHub API는 양자택일이 아니다.** 주소 또는 이벤트의 저장소·PR 식별자는 ‘무엇을 분석할지’를 정한다. 실제 내용과 코드 자료를 가져오는 수단은 서버의 GitHub API 호출이다. 브라우저에서 GitHub 웹페이지를 통째로 읽어 모델에 넘기는 구조가 아니다.

**서버**는 Next.js API route와 worker 등 AgentProof 백엔드 실행 코드다. GitHub와 모델 API 호출, 데이터 검사, 저장·전달을 담당한다. Vercel은 그 코드를 배포하는 환경이다. Preview 서버로 테스트 요청을 보내는 것은 이 제품 코드를 시험하는 방법이지, 서버의 존재 목적이 테스트라는 뜻은 아니다.

수동 경로 근거: `src/components/AnalyzeWorkspace.tsx`의 `runAnalysis` → `src/app/api/analyze/route.ts` → `src/lib/github.ts`의 `buildPullRequestInput` / `buildGitHubPullRequestInput`. 자동 경로도 `buildGitHubPullRequestInput`을 사용하지만 두 진입점의 옵션과 후속 처리까지 완전히 동일하지는 않다.

### 수집된 자료에서 검토 안내를 만드는 순서

아래는 새 검토 안내 경로다. 모든 기존 분석 분기를 하나의 LLM 흐름으로 설명한 것이 아니다.

1. **수집:** GitHub API에서 PR 본문·변경 파일·연결 Issue·check/status 등을 얻고 base/head를 기록한다. 추가 파일은 지정 commit의 Contents API로 읽는다.
2. **목표 해석:** LLM에 식별된 원문 구간을 주고 목표·조건 등을 제안하게 한다. 이 호출의 코드 후보 배열은 비워 둔다. 구현을 보고 목표를 역으로 만드는 혼선을 줄이기 위해서다. 원문 참조 검사가 의미 정확도까지 증명하지는 않는다.
3. **후보 준비:** diff 조각과 확보한 파일에서 목표 관련 코드 조각을 만든다. 불완전한 diff에 대한 자동 추가 읽기도 있다. 저장소 전체 검색은 아니다.
4. **첫 추천:** LLM이 목표·코드 조각·변경 파일 목록으로 관련 후보, 첫 확인 위치, 이유와 질문을 반환한다.
5. **추가 문맥:** 모델이 요청한 경로를 실제 commit에서 읽고 조각을 추출한다. 새 문맥이 있으면 한 번 더 추천한다. 이전의 유효한 후보·추천을 보존하는 로직과 입력 예산이 함께 있다. 무제한 추가나 별도의 최종 심판 모델을 매번 호출하는 구조는 아니다.
6. **표시 변환:** 형식·참조 검사와 문구 처리를 거쳐 카드 데이터로 변환한다. 코드/테스트/실행, 출처, 먼저 볼 위치와 질문을 구분한다.

현재 안내 경로에는 공개 저장소·provider 설정·분석 정책 등의 실행 조건이 있다. Private PR에도 동일한 LLM 흐름이 항상 제공된다고 설명하면 안 된다. 실패 후 보존되는 범위도 오류와 단계에 따라 다르므로 ‘어떤 실패든 모든 결과가 표시된다’고 보장하지 않는다.

근거: `src/lib/github.ts`, `src/lib/general-pr-observation-service.ts`, `src/lib/review-intent.ts`, `src/lib/review-snippets.ts`, `src/lib/gemini-navigation.ts`.

현재 코드에는 기존 strict 검증 보고서와 새로운 검토 안내 경로가 함께 존재한다. 하나의 경로에 있는 ‘충족 판정에 필요한 조건’을 다른 경로의 ‘관련 코드 보여주기’에 그대로 적용하면 유용한 카드까지 사라질 수 있다.

### 사용자에게 전달되는 결과

`src/lib/pr-evidence-review.ts`가 보고서를 검토 표시 모델로 바꾸고 `src/components/PrEvidenceReview.tsx`가 목표 또는 변경 요약을 표시한다. `ReportView.tsx`와 대시보드에 연결되어 있다. 카드에는 관련 위치·설명·질문과 GitHub 코드/check 링크가 있다. 이 확인 범위에서 ‘코드 보기’는 GitHub 참조 링크다. 앱 안에서 함수 전체를 자유롭게 탐색하는 전용 코드 뷰어가 완성됐다는 뜻이 아니다.

새 검토 안내 데이터가 있으면 전용 표시 경로를 우선하며, 표시할 목표가 없으면 변경 요약을 만든다. 이 데이터 자체가 없는 보고서는 기존 요구사항/후보 표시 경로를 따른다. 목표가 없다는 사실을 요구사항 미충족으로 바꾸지는 않는다. 저장·댓글·대시보드의 모든 운영 경로가 이번 코드 검토만으로 end-to-end 검증됐다는 뜻도 아니다.

## 3. 기술과 역할

| 기술 | AgentProof에서 배우는 역할 | 보장하지 못하는 것 |
|---|---|---|
| React / Next.js | 화면과 서버 API를 연결하는 웹 애플리케이션 구조 | 결과의 의미 정확도 |
| GitHub 로그인 / GitHub App | 사용자 접근과 저장소 연동 | 사용자 로그인과 앱의 저장소 접근 권한은 서로 다름 |
| Webhook | GitHub 이벤트 수신 | 자료 전체 수집이나 분석 완료 자체가 아님 |
| 작업 큐 / worker | 분석 작업을 등록하고 처리 | 작업 접수와 완료는 다름. 큐 사용은 설정에 따름 |
| TypeScript | 개발 중 데이터 타입과 함수 계약 검사 | 외부 JSON의 런타임 안전성 |
| 런타임 검증 | 실제 응답의 구조·참조·허용값 검사 | LLM 설명이 참이라는 보장 |
| Git / commit SHA | 분석한 코드 버전을 고정하고 변경 비교 | 그 코드가 올바르게 동작한다는 보장 |
| GitHub API | PR 본문, 변경 파일, Issue, check 등의 수집 | 모든 테스트가 실행됐다는 증명 |
| AST / 구조적 추출 | 코드의 선언·함수·블록 경계 파악 | 사용자의 의도나 동적 실행 경로 전체 |
| 검색·후보 선별 | 제한된 입력에 넣을 관련 위치 발견 | 선택 밖에 중요한 코드가 없다는 보장 |
| LLM | 원문 목표 해석, 코드 관련성·검토 순서 판단 | 사실·권한·실행 결과의 자동 인증 |
| Vitest | 특정 동작·계약의 회귀 테스트 | 실제 PR 전체의 의미 정확도 |
| Vercel / 환경변수 | 배포 환경과 서버 설정·비밀값 관리 | 로컬과 Preview가 자동으로 같은 설정임 |
| 저장 / 권한 검사 | 허용된 보고서 전달과 조회 | 분석 성공이 저장·게시 성공까지 보장하지 않음 |

개발 검증 도구인 TypeScript 타입 검사와 Vitest는 제품의 자료 수집 단계가 아니다. 개발자가 계약과 회귀를 점검하는 수단이다. 실제 외부 응답에는 런타임 검사도 필요하다.

package.json에서 Next.js, React, TypeScript, Vitest, OpenAI SDK, Google GenAI SDK를 확인했다. 현재 provider 선택 코드는 Gemini 키가 있으면 Google GenAI SDK로 직접 호출하며 OpenAI fallback도 있다. 호환 변수 `AI_GATEWAY_API_KEY`가 남아 있어도 Gemini 요청이 Vercel Gateway를 경유한다는 뜻은 아니다. 실제 배포 모델은 해당 환경 설정을 확인해야 한다. 과거 Luna, 개발을 돕는 Astra/Sol, 제품 모델은 별개다.

현재 코드 조각 경로에는 파일 256KiB, 최종 16조각·48,000바이트 등의 제한이 있다. 외울 상수가 아니라 ‘어느 단계의 무엇을 제한하는가’를 배우는 사례다. 모든 언어가 정밀 AST나 symbol resolution으로 처리된다고 생각하면 안 된다. Python에는 제한된 구조 스캐너와 fallback 경로가 있으며 현재 전역 저장소 검색이 완성됐다는 근거는 없다.

## 6. 권장 수업 순서

1. 제품 목적과 사용자 경험: 무엇을 판단하도록 돕고, 무엇은 판정하지 않는가.
2. GitHub 연동: 로그인·앱 권한·PR 이벤트·webhook·작업 처리.
3. 자료 수집: GitHub API, Issue/PR 출처, base/head, 오류와 누락.
4. 해석과 탐색: 목표 해석 → 코드 조각 → 추천 → 필요한 추가 읽기.
5. 결과 전달: 참조 검사·표시 변환·저장 보고서·댓글·대시보드.
6. 품질 검증: 단위 테스트, 실제 PR 평가, silver 판단, 과적합과 반복 변동.

앞 다섯 단계는 제품을 배우는 순서이며 여섯 번째는 개발자가 그 제품을 검증하는 방법이다. 최근 테스트 스크립트의 실행 순서를 전체 제품 구조로 설명하지 않는다. 03의 과거 설계와 분류 실험도 현재의 필수 처리 단계로 이어 붙이지 않는다.

각 수업의 완료 기준은 ‘기술 이름을 안다’가 아니라 입력·출력·실패 예시·대안을 자기 말로 설명할 수 있다는 것이다.
